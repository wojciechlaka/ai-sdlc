Refinement Engine — Architektur

AI-gestützte Ticket-Verfeinerung: Ein Agent analysiert Tickets gegen die Codebase und liefert strukturierte Implementierungspläne.

Browser (blau, oben rechts)

Die Web-Oberfläche unter localhost:5173. Von hier aus erstellst du Tickets, startest Refinements und beantwortest Rückfragen des Agenten. Gebaut mit React 19 + Vite.

packages/shared (gelb, unten)

Gemeinsame Zod-Schemas, die definieren, wie eine gültige Claude-Antwort aussehen muss. Wird sowohl vom Backend (Validierung) als auch vom Frontend (Typen) genutzt — die einzige direkte Abhängigkeit zwischen den beiden.

Backend (grün, große Box)

  • REST API — nimmt HTTP-Anfragen entgegen (Ticket erstellen, Refinement starten, Antwort einreichen)
  • Refinement Orchestrator — der Dirigent: koordiniert Repo-Laden → Summary → Agent → Statuswechsel
  • Repo Cache — klont das Git-Repository einmalig, zieht bei Folgeaufrufen nur noch git pull
  • Agent CLI — startet Claude als Subprocess (claude --print --output-format stream-json), liest die JSON-Antwort aus und validiert sie gegen das Zod-Schema; bei Fehler: automatischer Retry mit Fehlerkontext
  • Event Bus — interner Node.js EventEmitter; wenn Claude etwas ausgibt, landet es hier zuerst
  • SSE Layer — schickt Events live als Stream in den Browser (kein Polling nötig)
  • SQLite / Drizzle ORM — speichert Tickets, Agent-Runs, Audit-Events und Review-Entscheidungen dauerhaft

Extern (lila, links)

  • Git Repository — das zu analysierende Projekt (z.B. auf GitHub). Wird lokal gecacht.
  • claude CLI — das KI-Modell als Kommandozeilenprogramm. Bekommt den Prompt über stdin, liefert die Antwort als JSON-Stream über stdout zurück.

Die zwei Verbindungen zwischen Browser und Backend

↓ REST (Browser → Backend) Du schickst Befehle: Refinement starten, Antwort einreichen, Ticket anlegen. Klassische HTTP-Anfragen.
↑ SSE (Backend → Browser) Der Browser hält einen dauerhaften Kanal offen und bekommt live Updates: "Agent analysiert…", "Rückfrage: Mobile oder Web?", "Fertig — Plan liegt vor."

Wie der Event Bus funktioniert

Der Event Bus ist ein einzelnes Node.js EventEmitter-Objekt — kein externes System, keine Queue, nur ein In-Memory-Kanal. Er entkoppelt den Orchestrator vom SSE-Layer: beide kennen sich nicht direkt, sie teilen nur den Bus.

Ablauf
Orchestrator
  │ emit('progress', { ticketId, message })
  ▼
Event Bus (refinementEvents)
  │ on('progress', handler)
  ▼
SSE Layer
  │ stream.writeSSE({ data: JSON.stringify(...) })
  ▼
Browser
Drei Event-Typen
Event Wann
progress Claude analysiert gerade — Zwischenstand für den Nutzer
status Ticket wechselt Status, z.B. refining → review
question Claude stellt eine Rückfrage und wartet auf Antwort

Der SSE-Layer schaut bei jedem Event nach, ob für diese ticketId gerade ein Browser-Tab verbunden ist. Wenn ja → Event wird gestreamt. Wenn nein → Event wird verworfen.

Warum dieser Umweg? Der Orchestrator läuft fire-and-forget — der HTTP-Request ist längst beendet, wenn Claude noch arbeitet. Ohne den Bus müsste der Orchestrator den SSE-Layer direkt kennen und aufrufen. Mit dem Bus bleibt jedes Modul unabhängig.
