Refinement Engine — Architektur

AI-gestützte Ticket-Verfeinerung: Ein Agent analysiert Tickets gegen die Codebase und liefert strukturierte Implementierungspläne. Eine Next.js-App, Fachkern nach Ports & Adapters.

Browser (blau)

Die Web-Oberfläche unter localhost:3000. Hier legst du Tickets an, startest Refinements und beantwortest Rückfragen des Agenten. Jedes Ticket hat eine eigene URL (/tickets/T-1). React 19 Client Components für alles Interaktive: Live-Fortschritt, Timer, Rückfrage, Buttons.

packages/shared

Zod-Verträge zwischen Kern und UI: Ticket- und Run-DTOs, Eingaben (Ticket anlegen, Refine, Antwort), die drei Event-Typen und das Schema der Agent-Ausgabe. Der Kern validiert damit, die UI nutzt die Typen — es gibt keine von Hand nachgebauten API-Typen.

apps/web — Next.js 16, ein Prozess (grün)

  • Server Components — rendern Ticket-Liste und Ticket-Detail auf dem Server und rufen dafür direkt die Use Cases auf
  • Server Actions — Ticket anlegen, Refinement starten, Antwort senden, Stoppen, Löschen, Reset; danach wird die Seite neu geladen (revalidatePath)
  • SSE-Route /api/events — hält pro Browser-Tab einen Stream offen und reicht Ereignisse des Kerns durch
  • Composition Root lib/container.ts — erzeugt einmal pro Prozess die Engine (Datenbank, Adapter, Event-Bus) und hält sie auf globalThis

packages/core — Hexagon (orange)

  • Use Cases — die Fachabläufe: Ticket anlegen, Refinement starten, Rückfrage beantworten, Stoppen, Löschen, Reset; Agent-Läufe laufen im Hintergrund weiter
  • Domäne — reine Regeln ohne I/O: wann ein Refinement starten darf, wann eine Antwort angenommen wird, Aufbau des Frage-Antwort-Verlaufs, Fachfehler
  • Ports — Schnittstellen, die der Kern braucht: Repositories, Audit-Log, AgentRunner, RepoProvider, EventPublisher
  • Adapter — sqlite (Drizzle), git (Repo-Cache + Codebase-Summary), claudeCli (Agent als Subprocess, Zod-Validierung, ein Retry), nodeEvents (Event-Bus)
  • Abhängigkeitsregel — Domäne, Ports und Use Cases importieren keine Adapter; eine ESLint-Regel prüft das

Extern (lila)

  • SQLite-Datei — apps/web/data/refinement.db: Tickets, Agent-Läufe, Audit-Events
  • Git-Repository — das zu analysierende Projekt, z. B. der Conduit-Fork; wird lokal gecacht
  • claude CLI — bekommt den Prompt über stdin und liefert die Antwort als JSON-Stream über stdout

Die zwei Wege zwischen Browser und Server

↓ Server Actions (Browser → Server) Befehle wie „Refinement starten“ oder „Antwort senden“. Der Kern prüft und validiert, Fachfehler kommen als Meldung zurück in die Oberfläche.
↑ SSE (Server → Browser) Live-Ereignisse während eines Laufs: Fortschritt erscheint sofort im Log; bei Status-Wechsel oder Rückfrage lädt der Browser die Seite neu und zeigt den aktuellen Stand.

Wie der Event-Bus funktioniert

Der Event-Bus ist ein Port (EventPublisher) mit einem Adapter auf Basis eines Node.js-EventEmitter — ein Kanal pro Ticket, kein externes System. Use Cases und SSE-Route kennen sich nicht; beide sprechen nur mit dem Port. In Phase 3 wird nur der Adapter getauscht (z. B. Postgres LISTEN/NOTIFY).

Drei Event-Typen
Event Wann
progress Zwischenstand des Laufs — erscheint direkt im Log
status Ticket wechselt Status, z. B. refining → review — Seite wird neu geladen
question Der Agent stellt eine Rückfrage — Seite wird neu geladen und zeigt das Antwortfeld

Ist für ein Ticket gerade kein Tab verbunden, geht das Ereignis verloren — der Zustand selbst liegt in der Datenbank und wird beim Laden der Seite gelesen.

Warum dieser Umweg? Ein Agent-Lauf läuft im Hintergrund weiter, lange nachdem die Server Action geantwortet hat. Über den Port bleiben Fachlogik und Transport getrennt — der Kern weiß nichts von HTTP oder Browsern.
